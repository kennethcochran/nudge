# S2091 — XPath expressions should not be vulnerable to injection attacks

## Why
An XPath expression built by concatenating untrusted
input lets an attacker rewrite the query (`' or '1'='1` style boolean
injection, or navigating to nodes outside the intended scope) and read
or select data they shouldn't see. XPath has no universal escaping
function, so hand-rolled quoting is unreliable.

## Do this
1. Stop building the XPath expression by string concatenation.
2. Pass the untrusted value as a parameter: compile the expression with
   a variable (`$param`) and bind it via `XPathExpression.SetContext`
   with an `XsltContext` that resolves the variable, or use the
   equivalent parameter mechanism of your XPath API.
3. If the value genuinely must be embedded in the expression text,
   validate it against a strict allowlist first (e.g. digits only for
   an ID) and reject anything else.

## AVOID
- Do not escape quotes by hand (doubling `'`) or strip quote
  characters from the input — hand-rolled XPath quoting breaks on edge
  cases and gives false confidence.
- Do not validate with a blocklist of "dangerous" XPath tokens; use
  parameters or an allowlist.

- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
