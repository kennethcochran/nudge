# S2115 — A secure password should be used when connecting to a database

## Why
A connection string with a blank, default, or hardcoded password means anyone
who can read the configuration — or the repository history, forever — owns the
database. Credentials committed to source leak through clones, forks, and
backups long after the code is "fixed".

## Do this
1. Remove the password from the connection string everywhere it is committed
   (code, `appsettings.json`, constants).
2. Supply it at runtime from an uncommitted source: environment variable,
   user-secrets in development, a vault/KeyVault in production.
3. Give the application a least-privilege database login (not `sa`/admin), and
   rotate the credential that was exposed.
4. Verify the committed connection string contains no password and the app
   still connects using the runtime-supplied secret.

## AVOID
- Do not "fix" it by moving the hardcoded password into a different committed
   file (another config section, a constants class, a `.env` checked into
   git) — the secret is still in the repo. Uncommitted runtime configuration
   is the point.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
