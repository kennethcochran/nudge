# S3415 — Assertion arguments should be passed in the correct order

## Why
`Assert.AreEqual(expected, actual)` with the arguments flipped produces failure
messages that say the opposite of what happened — "Expected: 5, Actual: 3"
when the code actually produced 5. The next person debugging the failure
chases the wrong direction.

## Do this
1. Put `expected` first and `actual` second in classic-model assertions.
2. For constraint-model assertions (`Assert.That(actual, Is.EqualTo(expected))`),
   keep the actual value as the subject of the assertion.
3. Re-run the test and read a failure message to confirm it now describes
   reality.

## AVOID
- Do not "fix" it by migrating the whole test file to the constraint model
  "for consistency" — the fix is the argument order on the flagged assertion,
  not a style migration.
- Do not swap the arguments back and forth until the message "looks right" —
  decide from the semantics (what did you expect, what did the code produce),
  not from aesthetics.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
