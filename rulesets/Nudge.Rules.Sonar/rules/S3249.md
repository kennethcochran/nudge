# S3249 — Classes directly extending "object" should not call "base" in "GetHashCode" or "Equals"

## Why
For a class deriving directly from `object`, `base.GetHashCode()` is
reference-identity hashing and `base.Equals` is reference equality —
calling them from a value-based override mixes identity semantics into
value semantics. The classic failure: `Equals` compares fields but
`GetHashCode` calls `base.GetHashCode()`, so two equal objects hash
differently and dictionaries silently lose entries.

## Do this
1. In `GetHashCode`, hash exactly the fields used by `Equals` —
   `HashCode.Combine(Field1, Field2)` is the modern form.
2. In `Equals`, compare the same fields directly; don't delegate to
   `base.Equals` (reference equality) when you mean value comparison.
3. Add a test asserting `a.Equals(b)` implies
   `a.GetHashCode() == b.GetHashCode()` for representative instances —
   that's the contract the bug broke.

## AVOID
- Do not keep `base.GetHashCode()` and XOR your fields into it — the
  identity component still poisons the hash, and equal objects still hash
  differently per instance.
- Do not "fix" it by deleting the `Equals` override instead of fixing the
  hash; that trades a dictionary bug for lost value semantics.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
