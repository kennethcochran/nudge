# S7044 — Server-side requests should not be vulnerable to traversing attacks

## Why
Building a server-side URL or file path by concatenating user input lets an
attacker pivot the request: `..` segments escape the intended directory, and a
crafted host turns an internal fetch into SSRF — including hits against cloud
metadata endpoints from inside your own network. The rule flags request targets
assembled from untrusted strings.

## Do this
1. Never concatenate user input into a URL or path — build it from validated
   parts with `UriBuilder` / `Path.Combine`.
2. Validate the resolved result against an allowlist: permitted hosts for URLs;
   for files, resolve with `Path.GetFullPath` and confirm it stays under the
   intended root directory.
3. If the feature needs arbitrary user-supplied URLs, proxy them through a
   fetcher that blocks private, loopback, and link-local ranges and refuses to
   follow redirects into them.

## AVOID
- Do not "sanitize" by stripping `..` or `http://` substrings — attackers
  double-encode or use alternates like `....//`; validate the resolved value
  against an allowlist instead of blacklisting substrings.
- Do not fix the path case while the same concatenation still builds the URL
  host — the rule covers both, and SSRF via host injection is the worse hole.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
