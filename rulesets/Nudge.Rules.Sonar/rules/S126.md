# S126 — "if ... else if" constructs should end with "else" clauses

## Why
An `if` / `else if` chain with no `else` silently does nothing for
unanticipated values — new enum members, unexpected states, corrupted data all
fall through without a trace, and the resulting bug surfaces far from the
chain that caused it.

## Do this
1. Add a final `else` that handles the unexpected case explicitly: throw
   `InvalidOperationException` / `ArgumentOutOfRangeException` for values that
   should be impossible, or log-and-handle for tolerable ones.
2. Make the `else` do something observable — the point is that the unhandled
   case can never again pass silently.

## AVOID
- Do not add an empty `else { }` (or one containing only a comment) to satisfy
  the rule. An else clause that does nothing is the same silent fallthrough
  with compliant syntax — the unexpected case must be handled, not merely
  acknowledged.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
