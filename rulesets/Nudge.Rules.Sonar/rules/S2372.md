# S2372 — Exceptions should not be thrown from property getters

## Why
Getters are expected to be cheap, side-effect-free reads — and data binding,
serializers, and debuggers invoke them implicitly, on paths you don't control.
A throwing getter surfaces far from the real problem, in a stack trace that
points at the framework instead of your validation logic.

## Do this
1. Move the throwing validation into a method (`GetX()`, `EnsureXReady()`)
   that callers invoke deliberately.
2. Make the getter return a best-effort value, or cache a result that was
   validated eagerly (in the constructor or setter).
3. Validate inputs at *set* time — in the setter or constructor — instead of
   deferring the failure to read time.

## AVOID
- Do not catch the exception inside the getter and return a default — the
  validation still belongs in a method, and a getter that silently swallows
  is a getter that lies about the object's state.
- Do not "fix" it by converting the property to a method but keeping the
  throw on the implicit-read path (e.g., called from `ToString`) — the throw
  moved addresses; the contract violation didn't.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
