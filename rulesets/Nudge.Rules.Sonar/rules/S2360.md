# S2360 — Optional parameters should not be used

## Why
Optional parameter defaults are baked into *callers* at compile time. Change
the default later and already-compiled consumers keep using the old value with
no error — a silent behavioral break. They also complicate overload resolution
in ways that surface as bizarre compile errors after unrelated edits.

## Do this
1. Replace each optional parameter with an explicit overload that supplies the
   default value.
2. Put the real logic in the fullest overload; thinner overloads delegate to
   it.
3. Treat this as a binary-compatibility break in release notes either way —
   but overloads fail loudly at compile time instead of silently at runtime.

## AVOID
- Do not replace `= someDefault` with `= null` plus a null-coalescing body —
  that is the same baked-in default wearing a disguise, with a `null` nobody
  asked for in the signature.
- Do not keep the optional parameter and add an overload beside it "for
  safety" — two ways to call the same method is ambiguity, not safety.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
