# S7130 — First/Single should be used instead of FirstOrDefault/SingleOrDefault on collections that are known to be non-empty

## Why
Calling `FirstOrDefault()` on a collection your own logic has already
established as non-empty — then papering over the impossible null with `!` or
an unchecked dereference — lies in the type system. It claims emptiness is
possible when it isn't, and the null-forgiving operator hides the lie from the
compiler instead of removing it.

## Do this
1. Where non-emptiness is already established (an `Any()` check, a count
   check, construction logic), call `First()` / `Single()` directly.
2. Delete the now-dead null check and the `!` operator.
3. Keep `FirstOrDefault` / `SingleOrDefault` only where empty is genuinely
   possible — with a real empty-branch that does something meaningful.

## AVOID
- Do not keep `FirstOrDefault` and add `?? throw new InvalidOperationException()`
  — that is a hand-rolled `First()` that still misstates the contract to every
  reader of the code.
- Do not "establish" non-emptiness with a redundant `Any()` call right before
  `FirstOrDefault` just to justify keeping it — two enumerations to avoid one
  honest method call.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
