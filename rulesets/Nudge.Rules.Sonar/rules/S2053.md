# S2053 — Password hashing functions should use an unpredictable salt

## Why
A salt's entire job is to be unique per password and unpredictable. Hashing
with a fixed, hardcoded, or predictable salt (or none) lets an attacker
precompute one rainbow table and crack every password in the database at once.
Predictable "salts" like the username or the current time provide no such
protection.

## Do this
1. Generate a fresh random salt per password with
   `RandomNumberGenerator.GetBytes(...)` (16 bytes or more).
2. Store the salt alongside the hash in the same record — it is not a secret
   and must be available at verification time.
3. Use a real password-hashing function — PBKDF2 via `Rfc2898DeriveBytes`
   with a high iteration count, or a bcrypt/Argon2 library — never a single
   round of SHA-256.
4. Verify: hash the same password twice and confirm the hashes differ
   (different salts), and confirm login still verifies against the stored
   salt.

## AVOID
- Do not use the username, a constant string, or `DateTime.Now` as the salt —
   predictable salts defeat the purpose. Generate per-password randomness from
   `RandomNumberGenerator`.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
