# S108 — Nested blocks of code should not be left empty

## Why
An empty nested block (if / else / catch / finally / try) is ambiguous: is
'do nothing' the deliberate behavior, or is the implementation missing?
Neither readers nor future maintainers can tell, and neither can the
compiler. This rule flags blocks with no statements.

## Do this
1. If the block is intentionally empty, say why in a comment — e.g. why this catch is safe to ignore — or better, remove the block and narrow the surrounding construct.
2. If it is unfinished work, implement it now or delete it; do not leave scaffolding in the tree.
3. For an empty catch in particular, consider whether an exception filter or a narrower try expresses the intent without an empty handler at all.

## AVOID
- Do not drop a lone ';' or an empty comment into the block to make it 'non-empty' — the analyzer goes quiet and the ambiguity stays exactly as it was.
- Do not fill it with a no-op like Debug.WriteLine("") that pretends the case is handled.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
