# S3610 — Nullable type comparison should not be redundant

## Why
Calling `GetType()` on a `Nullable<T>` never returns `typeof(Nullable<T>)`:
if the nullable holds a value, `GetType()` returns the underlying value
type (`typeof(int)`); if it's null, `GetType()` throws
`NullReferenceException`. So a comparison like
`n.GetType() == typeof(int?)` is either always false or a crash — the
null/value question the author meant to ask got buried inside a type check
that cannot answer it. This rule flags `GetType()` comparisons against
nullable types.

## Do this
1. Ask the real question directly: `n.HasValue` / `n is null` for nullness,
   or compare `n.Value` / `n.GetValueOrDefault()` for the value.
2. Delete the `GetType()` call — it was never capable of distinguishing a
   null nullable from a valued one in the way the code assumed.
3. If the comparison was guarding real logic, make sure that logic's test
   still exercises the intended branch.

## AVOID
- Do not "fix" it by comparing against the underlying type instead
  (`n.GetType() == typeof(int)`). That's still a convoluted null check
  that throws on null — write `n.HasValue` and say what you mean.
- Do not "fix" it by inverting the comparison or tacking on `!` to flip the
  constant — a redundant check with the opposite polarity is still
  redundant. Write the condition the code actually intends.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
