# S6418 — Secrets should not be hard-coded

## Why
A secret baked into source code is compromised the
moment it is committed: it lives in git history forever, is visible to
everyone with repo access, and gets copied into builds, logs, and error
reports. Passwords, API keys, connection strings, and private keys do
not belong in code.

## Do this
1. Remove the hard-coded value from the source.
2. Read it at runtime from the environment, a secret manager (Azure Key
   Vault, AWS Secrets Manager, etc.), or a config file that is never
   committed (gitignored, deployed separately).
3. Rotate the exposed secret — assume it is already compromised.
4. Add the file/pattern to `.gitignore` and consider a pre-commit
   secret scan so it can't come back.

## AVOID
- Do not base64-encode the secret, split it across concatenated
  string fragments, or move it into a committed `appsettings.json` —
  the analyzer and any reader still see a hard-coded secret.
- Do not "fix" it by loading the secret from a file that ships with the
  repo; uncommitted-at-runtime is the requirement, not just
  out-of-source.

- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
