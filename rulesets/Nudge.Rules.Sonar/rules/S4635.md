# S4635 — Start index should be used instead of calling Substring

## Why
`s.Substring(start).IndexOf(c)` allocates an entirely new string just to search
within a slice of the original. The allocation is pure waste: the search never
needed its own string. Every `string` method that accepts a start index
(`IndexOf`, `LastIndexOf`, `StartsWith`, `Compare`, …) lets you search the
original in place, skipping the substring allocation completely. In a hot loop
— parsing, scanning, tokenizing — the throwaway substrings add up to real GC
pressure for zero benefit.

## Do this
1. Replace `s.Substring(start).IndexOf(x)` with `s.IndexOf(x, start)` — the
   overload that accepts a start index searches the original string directly.
2. Same pattern for the siblings: `s.Substring(start).LastIndexOf(x)` →
   `s.LastIndexOf(x, start)`, and check whether other `Substring`-then-inspect
   chains have start-index overloads available.
3. If you genuinely need the slice as a value (not just to search it), keep
   the `Substring` — or prefer `s.AsSpan()[start..]` to avoid the allocation.

## AVOID
- Do not "fix" this by replacing `Substring` with the range operator
  (`s[start..].IndexOf(x)`). The range slice still allocates a new string —
  you've modernized the syntax without removing the waste the rule targets.
- Do not cache the `Substring` result to amortize the cost — the allocation
  was never necessary in the first place.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
