# S4423 — Weak SSL/TLS protocols should not be used

## Why
Explicitly enabling SSL 3.0, TLS 1.0, or TLS 1.1 (e.g.
via `ServicePointManager.SecurityProtocol` or `SslProtocols`) opts the
connection into protocols with known, practical attacks (POODLE, BEAST,
weak cipher suites). A downgrade-capable peer or a man-in-the-middle
can then negotiate the weak protocol you left switched on.

## Do this
1. Find where the weak protocol is enabled and remove the explicit
   setting — on modern .NET the default negotiates the strongest
   protocol the OS supports (TLS 1.2+).
2. If you must pin, allow only `Tls12` and `Tls13`.
3. Check for the same pinning in config files, library defaults, and
   `HttpClientHandler.SslProtocols` — the flag must be gone everywhere,
   not just at the flagged call site.

## AVOID
- Do not set `SecurityProtocol = Tls12 | Tls11 | Tls | Ssl3` "for
  compatibility" — that re-enables exactly the weak protocols the rule
  flags.
- Do not leave a fallback path that retries over a weaker protocol when
  the strong handshake fails; the fallback is the vulnerability.

- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
