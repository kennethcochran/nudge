# S3875 — "operator==" should not be overloaded on reference types

## Why
Overloading `==` on a reference type breaks the null-check idiom — inside your
overload, `x == null` recurses into itself infinitely — and callers can't tell
reference equality from value equality. It also invites inconsistency with
`Equals` and `GetHashCode`.

## Do this
1. Don't overload `==` / `!=` on reference types; override `Equals` for value
   semantics and leave `==` as reference equality.
2. If value equality via `==` is truly required, implement the full pattern:
   override `Equals(object)` and `GetHashCode()`, implement `IEquatable<T>`,
   and only then add `==`/`!=` that delegate to `Equals` and use
   `ReferenceEquals` / `is null` for null checks.

## AVOID
- Do not "fix" it by deleting `==` but keeping `!=` (or vice versa) — the pair
  must stay consistent; remove or complete both together.
- Do not dodge the recursion with `(object)x == null` casts inside the
  overload — if you're fighting the operator that hard, the type shouldn't
  overload it.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
