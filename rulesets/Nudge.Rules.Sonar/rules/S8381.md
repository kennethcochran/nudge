# S8381 — "scoped" should be escaped when used as an identifier or type name in parenthesized lambda parameter lists

## Why
`scoped` became a contextual keyword (the `scoped` ref modifier). In a
parenthesized lambda parameter list, `(scoped x) => ...` parses `scoped` as the
modifier rather than your identifier — silently changing the parameter's
meaning or producing confusing compile errors far from the real problem.

## Do this
1. If the name is yours to change, rename the identifier to something that
   isn't a contextual keyword — the clearest fix.
2. If the name must stay (generated code, public API surface), escape it:
   `@scoped`, which forces the identifier reading.
3. Search for other uses of `scoped` as an identifier in lambda parameter lists
   in the same file; the keyword collision applies everywhere it appears.

## AVOID
- Do not "fix" it by removing the parentheses around a single lambda parameter
   to change how the line parses — that hides the ambiguity instead of
   resolving it.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
