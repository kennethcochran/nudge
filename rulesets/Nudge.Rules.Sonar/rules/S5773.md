# S5773 — Types allowed to be deserialized should be restricted

## Why
Deserializers that resolve arbitrary types from the payload (`BinaryFormatter`,
JSON with `TypeNameHandling`, `NetDataContractSerializer`) execute
attacker-controlled type graphs during deserialization — a direct path to
remote code execution. Restricting which types may be materialized is the
mitigation when deserialization itself can't be avoided.

## Do this
1. Prefer formats with no type resolution at all (`System.Text.Json` with
   default settings) — no declared type names, nothing to exploit.
2. If binary deserialization is required, install a `SerializationBinder` that
   allowlists the expected types and rejects everything else.
3. Reject payloads declaring types outside the allowlist before materializing
   any object graph.

## AVOID
- Do not deserialize first and check the resulting object's type afterward —
  the gadget chain runs *during* deserialization, so post-hoc validation is
  too late.
- Do not "restrict" by catching the exception a malicious payload throws —
  some payloads don't throw, they execute.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
