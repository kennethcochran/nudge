# S6507 — Blocks should not be synchronized on local variables

## Why
`lock (localVar)` locks on an object nobody else can ever see: each call gets
its own lock instance, so the critical section is never actually mutually
exclusive. Concurrent threads walk straight through, and the `lock` gives false
confidence that shared state is protected.

## Do this
1. Replace the lock object with a shared one: a `private readonly object _sync
   = new();` field on the containing instance (or a `static` one if the
   protected state is static).
2. Keep the locked region as small as possible — only the shared-state access.
3. If the intent was per-call isolation rather than protecting shared state,
   remove the `lock` instead of faking one.

## AVOID
- Do not "fix" it by locking on `this`, a string literal, or a `Type` object.
   `lock (this)` exposes your lock to external code (deadlock risk); locking
   on interned strings or `Type` objects creates process-wide contention.
   Use a private dedicated lock object.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
