# S134 — Control flow statements "if", "switch", "for", "foreach", "while", "do" and "try" should not be nested too deeply

## Why
Deep nesting multiplies the paths through a method: each level doubles what a
reader must hold in their head and what tests must cover. It is also where
bugs hide — the innermost branch is the least-tested and the hardest to
reason about.

## Do this
1. Extract inner blocks into well-named private methods, one level per
   concept.
2. Flatten with guard clauses: handle the edge cases with early returns at
   the top so the main path stays at the outermost level.
3. If the nesting is really type-switching in disguise, consider
   polymorphism or a strategy/dispatch table instead of nested conditionals.
4. Re-run the tests; extraction should be behavior-preserving.

## AVOID
- Do not merge the nested conditions with `&&` just to drop the nesting
   count — the complexity is still there, now compressed into one unreadable
   boolean. Extract methods or use guard clauses instead.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
