# S2083 — I/O function calls should not be vulnerable to path injection attacks

## Why
A path built from untrusted input and handed to a file
I/O call lets an attacker escape the intended directory (`..`,
absolute paths, UNC shares) and read or overwrite arbitrary files.
`Path.Combine` and `Path.GetFullPath` do not enforce a base directory —
they happily resolve a traversal into a valid absolute path.

## Do this
1. Treat any path component derived from outside input as tainted.
2. Resolve the final absolute path with `Path.GetFullPath`, then verify
   it starts with the intended base directory (plus separator); reject
   the request if it does not.
3. Better still, don't let the user name files at all: map input to a
   fixed allowlist of known file names, or strip every directory
   separator and keep only the file name via `Path.GetFileName` before
   combining.
4. Reject (don't sanitize) input that contains separators, `..`, drive
   letters, or `~` when a plain file name is expected.

## AVOID
- Do not "sanitize" by stripping a hard-coded list of bad substrings
  (`..`, `/`, `\`) — attackers bypass blocklists with encodings
  (`%2e%2e`), mixed separators, and absolute paths.
- Do not pass the tainted value through `Path.Combine` and assume the
  result is safe — `Combine` performs no containment check.

- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
