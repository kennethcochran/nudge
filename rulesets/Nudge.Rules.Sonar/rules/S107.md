# S107 — Methods should not have too many parameters

## Why
A method with seven or more parameters is a concept begging for a name.
Callers get the argument order wrong, adding a parameter later breaks every
call site, and the test matrix explodes. Long parameter lists also signal the
method is doing several things at once.

## Do this
1. Group related parameters into a small parameter object or record with a
   meaningful domain name — one that carries its own invariants, not just a
   bag of fields.
2. If some parameters are flags that switch behavior, split the method into
   separate methods instead.
3. After the change, each parameter should be hard to confuse with its
   neighbors.

## AVOID
- Do not introduce a `FooParams` bag that merely renames the parameter list.
   A parameter object must represent a real domain concept; wrapping the
   same seven unrelated values in a struct keeps all the complexity and adds
   a type on top of it.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
