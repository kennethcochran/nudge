# S6966 — Await the Async Version Instead of Blocking

## Why
Calling a synchronous blocking method (like `File.ReadAllText`) inside an
`async` method defeats the purpose of async: the thread pool thread sits
blocked waiting on I/O instead of being freed to do other work. Under load
this causes thread pool starvation — requests queue, latency spikes, and the
application stops scaling. The async version (`ReadAllTextAsync`) exists
precisely so the thread is released while the I/O completes.

## Do this
1. Replace the blocking call with its async counterpart and `await` it:
   `File.ReadAllText` → `await File.ReadAllTextAsync`.
2. Let the async pattern propagate: if the caller is async, the awaited call
   keeps the whole chain non-blocking.
3. If no async version exists and the work is genuinely I/O-bound, that's a
   design smell worth noting — don't paper over it.

## AVOID
- Do not wrap the blocking call in `Task.Run(() => ...)` just to get an
  awaitable. That moves the blocking to a pool thread — the thread is still
  blocked, you've just hidden where.
- Do not add `await Task.CompletedTask;` to silence the diagnostic while
  keeping the blocking call. The method is still synchronous in behavior.
- Do not remove `async` and return a completed task to dodge the rule when
  the operation is genuinely I/O-bound — you've made the blocking invisible
  to callers instead of fixing it.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
