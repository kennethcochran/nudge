# S6802 — Using lambda expressions in loops should be avoided in Blazor markup section

## Why
A lambda inside a Blazor @foreach/@for loop in markup allocates a new
delegate per item per render, and it closes over the loop variable — so every
button can end up invoking the handler with the last item, or re-rendering
churns through garbage. This rule flags lambdas in loop markup.

## Do this
1. Extract the lambda body into a component method and reference it as a method group instead of an inline lambda.
2. If the handler needs the item, pass it as a component parameter or capture a per-iteration local into a named method — not an inline lambda in the loop.
3. For lists, prefer a child component per row; the render diff then works per item instead of rebuilding delegates.

## AVOID
- Do not hoist the lambda into a local outside the loop while still capturing the loop variable — every delegate closes over the same variable and every button acts on the last item; nothing is fixed.
- Do not keep the inline lambda in the markup but copy the loop variable to a local — the per-render allocation, the cost the rule targets, remains.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
