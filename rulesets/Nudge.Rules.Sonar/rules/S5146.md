# S5146 — HTTP request redirections should not be open to forging attacks

## Why
A redirect target built from request data (`returnUrl`, `next`, a query
parameter) lets an attacker craft a link on your domain that bounces the victim
to a phishing site. Users trust your domain in the address bar, click through,
and hand credentials to the attacker's page.

## Do this
1. Before redirecting, validate with `Url.IsLocalUrl(returnUrl)` and redirect
   only when it returns true.
2. If off-site redirects are a real requirement, validate the target against an
   explicit allowlist of hosts and paths — never a free-form URL.
3. On validation failure, redirect to a safe default page and log the rejected
   URL so abuse is visible.

## AVOID
- Do not validate with `url.StartsWith("https://mysite.com")` — it is
  bypassed by `https://mysite.com.evil.com`, userinfo tricks
  (`https://mysite.com@evil.com`), and encoded variants.
- Do not allowlist only the scheme (`http`/`https`) — the scheme was never the
  dangerous part; the destination host is.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
