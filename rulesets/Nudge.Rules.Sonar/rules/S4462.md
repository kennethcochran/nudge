# S4462 — Calls to "async" methods should not be blocking

## Why
`.Result` / `.Wait()` on an async method blocks the calling thread until
completion — on a UI thread or an ASP.NET request with a captured
`SynchronizationContext`, the continuation can't run on the blocked thread and
you deadlock. Even without a deadlock, you're holding a thread hostage doing
nothing.

## Do this
1. Make the calling method `async` and `await` the call — push async all the
   way up to the entry point (`async Main`, async controller action).
2. At a genuinely synchronous boundary (a constructor), don't block — use an
   async factory method or an explicit async initialization step instead.

## AVOID
- Do not "fix" it with `Task.Run(() => DoAsync()).Result` — you've added a
  thread-pool hop to the same blocking wait; the deadlock risk moves, it
  doesn't leave, and you've added pool pressure.
- Do not add `.ConfigureAwait(false)` to the inner call and keep `.Result` —
  it dodges the classic context deadlock but the thread is still blocked and
  thread-pool starvation remains.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
