# S7131 — A write lock should not be released when a read lock has been acquired and vice versa

## Why
`ReaderWriterLockSlim` tracks read and write lock
holdings separately. Releasing a write lock when you hold a read lock
(or vice versa) throws `SynchronizationLockException` at runtime — and
worse, mismatched acquire/release pairs corrupt the lock's accounting,
so the failure surfaces far from the mistake.

## Do this
1. Match every acquire with its own release: `EnterReadLock` pairs
   only with `ExitReadLock`; `EnterWriteLock` only with `ExitWriteLock`.
2. Put the release in a `finally` block so exceptions can't leak a held
   lock.
3. If the method upgrades from read to write, use `EnterUpgradeableReadLock`
   with its matching exit — don't improvise the pairing.

## AVOID
- Do not "fix" it by releasing both locks (`ExitReadLock();
  ExitWriteLock();`) "to be safe" — releasing a lock you don't hold
  throws.
- Do not mix the pairs even inside `try/finally`; the pairing is the
  fix, the `finally` only makes it exception-safe.

- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
