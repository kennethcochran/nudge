# S6680 — Loop boundaries should not be vulnerable to injection attacks

## Why
When a loop's bound comes from outside the trust boundary — request data, a
file, a deserialized payload — an attacker controls the iteration count. A
huge bound turns the loop into a denial-of-service; a negative or wrapped
bound can skip validation logic entirely. The rule flags loop limits whose
values can be attacker-influenced.

## Do this
1. Trace the bound back to its source. If it can originate outside your
   control, treat it as hostile input.
2. Validate and clamp it to a sane maximum before the loop starts.
3. Where possible, iterate the collection itself (`foreach`) instead of
   trusting an externally supplied count.
4. Keep the validation adjacent to the loop so a later reader sees the bound
   is intentional, not incidental.

## AVOID
- Do not launder the bound through a local variable, a parse-then-copy, or
  an intermediate property to break the dataflow the analyzer sees. The taint
  is still there; you have only blinded the detector.
- Do not "clamp" by narrowing the type (e.g. casting a `long` bound to `int`).
  A value that overflows the cast wraps around and can produce a negative or
  tiny bound — a different bug, not a fix.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
