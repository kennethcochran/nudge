# S5144 — Server-side requests should not be vulnerable to forging attacks

## Why
Passing request input into `HttpClient`/`WebRequest` lets an attacker make your
server fetch arbitrary URLs — probing internal endpoints (cloud metadata at
169.254.169.254, intranet services) with your server's network position and
credentials. This is server-side request forgery.

## Do this
1. Never build the request URI from raw request input; resolve user choices to
   server-side-known URLs (a lookup table of allowed targets).
2. If the host must be dynamic, validate it against an explicit allowlist and
   reject non-public IP ranges after DNS resolution — and re-validate at
   connection time, since DNS rebinding can swap the answer between check and
   use.
3. Restrict schemes to `http`/`https` and strip any userinfo
   (`user:pass@host`) from the URI.

## AVOID
- Do not "fix" it with a blocklist of `localhost`, `127.0.0.1`,
  `169.254.169.254` — decimal/octal/hex IP forms, `0.0.0.0`, IPv6 variants,
  and DNS rebinding all sail past string blocklists. Allowlists, not
  blocklists.
- Do not validate the hostname string but then let the HTTP stack re-resolve
  it later — validate the address that is actually connected to.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
