# S1133 — Deprecated code should be removed

## Why
`[Obsolete]` members kept "just in case" rot: callers keep compiling against
them, new developers copy the old pattern, and the eventual removal becomes a
bigger break than it needed to be. Deprecation is a migration notice, not a
permanent state.

## Do this
1. Check whether anything still calls the obsolete member; migrate those
   callers to the replacement first.
2. Delete the obsolete member — and its tests and docs — once nothing
   references it.
3. If external consumers need a grace period, keep the `[Obsolete]` warning
   for one release cycle with a stated removal date, then remove it.

## AVOID
- Do not "fix" it by removing the `[Obsolete]` attribute and keeping the code
  — you've un-deprecated a dead API instead of deleting it.
- Do not leave the member in place because "someone might use it" — that's
  what source-control history is for.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
