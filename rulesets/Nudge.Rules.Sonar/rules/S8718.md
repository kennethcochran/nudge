# S8718 — Client-evaluated default values should use database functions

## Why
In EF Core, HasDefaultValue(DateTime.Now) — or Guid.NewGuid(), or any other
client-side expression — is evaluated once, on the client, when the migration
is scaffolded, and the resulting constant is baked into the migration. Every
row inserted later gets that same stale timestamp instead of 'now'. This rule
flags client-evaluated default values.

## Do this
1. Replace HasDefaultValue(<client expression>) with HasDefaultValueSql(...) using a database function, e.g. GETUTCDATE(), SYSDATETIME(), or NEWID() / gen_random_uuid().
2. Re-scaffold or hand-edit the affected migration so the SQL default replaces the baked-in constant.
3. Prefer UTC functions over local-time ones so stored values never depend on the database server's timezone.

## AVOID
- Do not switch DateTime.Now to DateTime.UtcNow and call it fixed — it is still evaluated once on the client and baked in; the staleness is the bug, not the timezone.
- Do not compute the value into a static readonly field — same single-evaluation problem with extra steps.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
