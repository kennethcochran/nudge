# S2743 — Static fields should not be used in generic types

## Why
A static field on Foo<T> isn't one field — the runtime creates a separate
copy per closed generic type, so Foo<int>.Cache and Foo<string>.Cache are
different storage that merely look shared. Code written as if it's one
global gets per-type silos instead. This rule flags statics in generic
types.

## Do this
1. Decide the intended sharing. One value for all T: move the static to a non-generic base class or a dedicated non-generic holder type.
2. If per-type storage is actually what you want, say so explicitly — e.g. a ConcurrentDictionary<Type, ...> on a non-generic holder, or documentation of the per-instantiation semantics.
3. Check every read and write of the field under the new sharing model; the semantics changed by definition.

## AVOID
- Do not make the field an instance field — instances don't share at all, which is a different (and usually wrong) semantic from either intended option.
- Do not move the static to a non-generic nested class but keep treating it as per-T; the silo just moved.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
