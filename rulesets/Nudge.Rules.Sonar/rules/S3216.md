# S3216 — "ConfigureAwait(false)" should be used

## Why
In library code, `await` captures the current `SynchronizationContext` by
default. If a consumer then blocks on the task (`.Result`, `.Wait()`) from a UI
or legacy ASP.NET context, the continuation can't get back onto the blocked
thread — deadlock. `ConfigureAwait(false)` says "resume on any thread", which
is what library code wants.

## Do this
1. Add `.ConfigureAwait(false)` to *every* `await` in the library method — not
   just the flagged line; each await captures independently.
2. Leave it off in UI-layer code that must resume on the UI thread (event
   handlers updating controls).
3. Never introduce `.Result`/`.Wait()` to "fix" a deadlock — blocking is the
   deadlock, not the cure.

## AVOID
- Do not add `ConfigureAwait(false)` only to the single await the analyzer
   flagged while leaving sibling awaits capturing — the deadlock just moves
   one line down; apply it to every await in the method.
- Do not "fix" a deadlock by replacing `await` with `.Result` or
   `.GetAwaiter().GetResult()`; that *is* the deadlock pattern.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
