# S3649 — Database queries should not be vulnerable to injection attacks

## Why
SQL assembled by concatenating untrusted input is the classic injection:
`' OR '1'='1` turns a login lookup into a tautology, and stacked queries can
exfiltrate or destroy data. The rule fires when a query string incorporating
outside data reaches a database command without parameterization.

## Do this
1. Trace the flagged query string back to its inputs and list which parts are
   untrusted.
2. Rewrite it as a parameterized query: fixed SQL text with `@param`
   placeholders, values passed via `Parameters.Add` (or the ORM's parameter
   mechanism) — never interpolated into the string.
3. For parts that cannot be parameters (table/column names, sort direction),
   restrict them to a hardcoded allowlist and reject anything else.
4. If you use an ORM, stay on its parameterized paths (LINQ,
   `FromSqlRaw`/`FromSqlInterpolated` with parameters) rather than dropping to
   raw concatenated SQL.

## AVOID
- Do not "fix" it with string escaping (`Replace("'", "''")`) — escaping is
  dialect-specific and bypassable; parameters are the fix.
- Do not allowlist the table name but keep concatenating the WHERE-clause
  values — parameterize every value, every time.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
