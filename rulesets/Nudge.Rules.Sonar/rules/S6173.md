# S6173 — Reflection should not be vulnerable to injection attacks

## Why
The rule fires when untrusted input reaches reflection APIs like
`Type.GetType(name)`, `Assembly.Load`, or `Activator.CreateInstance`. A
crafted type or assembly name can load attacker-chosen code into your
process — it is deserialization-adjacent: outside input decides what code
runs. A `try`/`catch` around the call doesn't help; the attacker's type name
resolves cleanly, and exceptions only catch typos.

## Do this
1. Replace the open-ended lookup with a static allow-list: map each accepted
   input value to a known `Type` object and reject anything else.
2. If the set must be extensible, resolve names only within a fixed, trusted
   assembly and namespace, and validate the name against a strict pattern
   before resolving.
3. Never pass raw user input to `Assembly.LoadFrom`/`LoadFile` — load only
   from application-controlled paths.

## AVOID
- Do not catch the exception from a bad type name and treat that as
  validation — an attacker's type name resolves successfully; the catch only
  fires on mistakes, not malice.
- Do not check that the string merely "starts with" your namespace and call
  it safe; nested-type syntax (`+`) and assembly-qualified names can smuggle
  unexpected targets past a prefix check.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
