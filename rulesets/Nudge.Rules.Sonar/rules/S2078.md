# S2078 — LDAP queries should not be vulnerable to injection attacks

## Why
LDAP search filters built by concatenating user input let an attacker rewrite
the filter's logic — `(uid=USER)` becomes `(uid=*)(objectClass=*)` and the whole
directory is dumped, or an authentication check is bypassed. The rule fires when
a filter string incorporating untrusted data reaches an LDAP query.

## Do this
1. Find every place a filter string is assembled from outside data (search
   boxes, login forms, synced attributes).
2. Escape special characters in each untrusted value per RFC 4515 (`*`, `(`,
   `)`, `\`, NUL) before interpolation — or use a library routine that does
   the full escaping.
3. Better: use a parameterized/safe LDAP API where the filter structure is
   fixed and values are bound separately, so input can never change the query's
   shape.
4. Add a test feeding filter metacharacters (`*)(uid=*`) and assert they are
   treated as literal text, not filter syntax.

## AVOID
- Do not "escape" with a hand-rolled replace covering only `*` — LDAP
  injection also rides on `(`, `)`, `\`, and NUL bytes; apply the full
  RFC 4515 escaping.
- Do not validate input with a blocklist of "bad substrings" — attackers encode
  around blocklists; escaping or binding is the fix.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
