# S5766 — Serializable objects should validate data during deserialization

## Why
Deserialization bypasses constructors, so a crafted stream can materialize
an object whose fields violate every invariant the constructors enforce —
negative balances, null required references, out-of-range enums. If nothing
re-checks those invariants after the formatter runs, the invalid object flows
straight into business logic. This rule flags [Serializable] types with no
validation on the deserialization path.

## Do this
1. Add an [OnDeserialized] method (or validate inside the ISerializable deserialization constructor) that re-asserts every invariant the constructors enforce, throwing SerializationException on violation.
2. Keep the checks in one place: have constructors and the deserialization path call the same validation routine so the two cannot drift apart.
3. Validate the whole graph, not just the root — nested objects and collections get their invariants checked too.

## AVOID
- Do not add an empty [OnDeserialized] method just to satisfy the detector — a no-op handler is the textbook cosmetic fix and changes nothing.
- Do not rely on property setters for validation; deserialization writes fields directly and never calls them.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
