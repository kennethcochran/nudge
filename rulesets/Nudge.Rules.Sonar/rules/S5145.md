# S5145 — Logging should not be vulnerable to injection attacks

## Why
User-controlled data written to a log can inject fake
log lines (log forging) via embedded carriage returns / line feeds: an
attacker crafts input containing `\r\n` so their text appears as a
separate, trusted-looking log entry — or overwrites the real line with
a lone `\r`. Downstream log parsers, SIEM rules, and anyone reading the
log can be misled.

## Do this
1. Find the tainted value the diagnostic flags and sanitize it at the
   point it is logged, not once at input time (the same value can reach
   other sinks).
2. Replace `\r` and `\n` (and other control characters) in the value
   before it reaches the log call, e.g. `value.Replace("\r","").Replace("\n","")`,
   or encode them.
3. Prefer structured logging (`logger.LogInformation("User {Name} ...", name)`)
   with a sink that encodes control characters, over string
   interpolation of raw values.
4. Validate the value against an allowlist (expected characters/format)
   when the domain permits it.

## AVOID
- Do not strip only `\n` while leaving `\r` — a lone carriage return
  still lets an attacker overwrite the line.
- Do not move the interpolation to a different logging call that still
  embeds the raw value; the sink is what matters, not the method name.

- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
