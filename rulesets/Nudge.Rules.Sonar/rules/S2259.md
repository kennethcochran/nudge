# S2259 — Null pointers should not be dereferenced

## Why
The analyzer's dataflow has found a path where a null reference is
dereferenced — that is a `NullReferenceException` in production. It usually
means a missing validation or a wrong assumption about a method's contract,
and the crash will surface far from whatever made the value null.

## Do this
1. Read the flagged dereference and trace where the null comes from: a
   parameter, a return value, an uninitialized field.
2. Fix at the source if the null is a bug (initialize it, fix the producer);
   otherwise guard at the use — an explicit null check, `?.` propagation, or
   `ArgumentNullException.ThrowIfNull` for parameters.
3. If a method's contract guarantees non-null, express it with nullable
   annotations (`T` vs `T?`) so the compiler enforces it instead of the
   analyzer catching it later.
4. Add a test for the null path.

## AVOID
- Do not slap the null-forgiving operator `!` on the dereference to silence
   the analyzer — the exception still happens at runtime; you've only hidden
   the diagnostic. Fix the null, don't deny it.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
