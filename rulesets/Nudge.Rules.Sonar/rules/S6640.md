# S6640 — Unsafe code blocks should not be used

## Why
`unsafe` blocks with raw pointers opt out of the CLR's memory safety — bounds
checks, type safety, and GC tracking are all bypassed. A single off-by-one
becomes memory corruption or an exploitable crash, and the JIT cannot verify
the code the way it verifies everything else.

## Do this
1. Replace the pointer arithmetic with safe equivalents: `Span<T>` /
   `Memory<T>`, `MemoryMarshal` helpers, or `stackalloc` consumed as a span.
2. If the unsafe block was written for performance, measure first — spans
   usually match pointer speed with safety intact.
3. Remove the `unsafe` block (and the `/unsafe` need for that code) once the
   rewrite is in place.
4. Run the full test suite, especially tests that exercised the unsafe path.

## AVOID
- Do not keep the `unsafe` block and just shrink it, rename variables, or
   move it into a helper — the memory-unsafety remains wherever the pointers
   are. Rewrite the operation with `Span<T>` or the safe APIs.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
