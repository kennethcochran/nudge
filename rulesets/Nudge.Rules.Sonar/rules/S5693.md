# S5693 — HTTP request content length should be limited

## Why
An endpoint that reads a request body with no size cap lets an attacker exhaust
server memory or disk with a single giant POST — a trivial denial of service.
Kestrel ships with defaults, but custom middleware, manual body reads, or
raised limits can silently remove the guard on exactly the endpoints attackers
probe.

## Do this
1. Find the flagged endpoint or body-read that has no size cap.
2. Apply a limit sized to the feature's real maximum payload:
   `[RequestSizeLimit(...)]` / `[RequestFormLimits(...)]` on the action, or
   `KestrelServerOptions.Limits.MaxRequestBodySize` /
   `IHttpMaxRequestBodySizeFeature` for broader scope.
3. Return 413 for oversize bodies (the framework does this automatically when
   the limit is set through its APIs).
4. Test that a body above the limit is rejected and a legitimate max-size body
   still succeeds.

## AVOID
- Do not set the limit to `long.MaxValue`, `null` (unlimited), or an absurdly
   large number to silence the diagnostic — an unlimited body *is* the
   vulnerability. Pick the smallest limit the feature actually needs.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
