# S4036 — OS commands should not rely on PATH resolution

## Why
Launching a process by bare name (`Process.Start("mytool")`) makes the OS
search `PATH` — and `PATH` is attacker-influenced (current directory on
Windows, writable directories, hijacked environment variables). A planted
executable with the right name then runs with your process's privileges instead
of the intended tool.

## Do this
1. Resolve the executable to an absolute path before launching: a known system
   directory (`Environment.SystemDirectory`), the application's own install
   directory, or a configured-and-validated location.
2. Validate the resolved file exists and, where it matters, that it's the
   binary you expect (strong name/signature, hash, or at minimum the exact
   directory you control).
3. Quote and escape arguments properly so the resolved path plus arguments
   can't be reinterpreted by a shell.

## AVOID
- Do not "resolve" the path by shelling out to `which`/`where` — that performs
   the same vulnerable `PATH` lookup yourself and passes the result along.
- Do not prepend a trusted directory to `PATH` at runtime and keep launching by
   bare name; any other `PATH` entry can still shadow it.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
