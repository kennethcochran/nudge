# S6776 — Stack traces should not be disclosed

## Why
Returning exception details or stack traces to a client — in an API error
body, an HTML error page in production, or a message that echoes input back —
hands attackers file paths, library versions, and internal call structure
that help them craft the next exploit. Production clients need a generic
error and a correlation ID; the details belong in server-side logs.

## Do this
1. Find where the exception text or stack trace reaches the response and cut
   that path.
2. Return a generic message plus a correlation/activity ID the client can
   quote to support.
3. Log the full exception, with stack trace, server-side against that ID.
4. Confirm detailed error pages (e.g. the developer exception page) are
   enabled only in the Development environment.

## AVOID
- Do not "fix" this by trimming the trace to the first frame or stripping
  file paths and line numbers. Partial disclosure still leaks internals —
  the fix is to not return it at all, not to return less of it.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
