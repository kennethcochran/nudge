# S3887 — Mutable, non-private fields should not be "readonly"

## Why
`public readonly List<string> Items` promises immutability it can't keep —
`readonly` freezes only the *reference*; anyone can still `Items.Add(...)` or
`Items.Clear()`. Callers see "readonly" and assume a safety the field doesn't
provide, and the mutation happens far from any code that looks responsible.

## Do this
1. Make the field `private readonly` and expose it as a property returning
   `IReadOnlyList<T>` (or `ReadOnlyCollection<T>` / an immutable type).
2. If external mutation is genuinely part of the API, drop `readonly` and
   document the mutability honestly — don't let the keyword lie.
3. Check every external use of the field; each one must go through the new
   property.

## AVOID
- Do not "fix" it by changing the field type to a custom collection subclass
   that still exposes mutation — the promise is still broken; expose a
   read-only view.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
