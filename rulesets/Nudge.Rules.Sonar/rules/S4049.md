# S4049 — Properties should be preferred

## Why
A public, parameterless method named `GetX()` that returns a value is a
property wearing a method's clothes: callers must write `obj.GetCount()`
instead of `obj.Count`, it can't participate in data binding or appear on
interfaces the way a property can, and every reader has to wonder whether
the method does something a property couldn't. This rule flags public
methods with no parameters, a non-void return, and a `Get`-prefixed name
("Consider making method '{0}' a property.").

## Do this
1. Convert the method to a read-only property: `public int Count => _count;`
   (or `{ get; }` with the logic in the getter).
2. Keep it a method only if it genuinely does work a property shouldn't —
   expensive computation or observable side effects — and even then,
   reconsider the `Get` prefix if it isn't simply retrieving a value.

## AVOID
- Do not dodge the rule by renaming `GetCount()` to `Count()` and keeping
  it a method. The name check goes quiet, but callers still face a method
  where a property belongs — the un-idiomatic surface is the problem, not
  the prefix.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
