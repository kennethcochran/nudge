# S2696 — Instance members should not write to "static" fields

## Why
When an instance method writes a static field, every instance shares one
mutable slot: the value any caller sees depends on which instance wrote
last, and on timing between threads. The code reads as if each object owns
its state, but the state is class-level. That mismatch is the bug farm —
callers reason per-instance while the runtime shares.

## Do this
1. Decide what the state belongs to. If it is per-instance, make the field
   an instance field. If it is genuinely shared, the write belongs in a
   static member — move the writing logic there so the sharing is explicit
   in the API, not hidden inside instance calls.
2. After moving ownership, check the sibling members: a flagged write
   usually means the reads are racy too, and they need the same treatment.
3. If the shared-state design is kept, add a test that hammers the member
   from multiple threads; the race this rule warns about is exactly what
   the test should try to trigger.

## AVOID
- Do not wrap the write in `Interlocked`/`lock` and call it fixed. Thread
  safety does not change ownership: an instance method mutating class-level
  state is still the design this rule flags, and the detector still fires.
  Guarding the race is not the same as fixing the sharing.
- Do not make the instance method static to silence the rule while callers
  still treat the state as per-instance — the sharing hazard is unchanged,
  only the detector moved.
- Do not move the static field onto a singleton instance — same shared
  mutable state, new address.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
