# S8949 — The overload accepting a 'CancellationToken' should be used

## Why
Calling the tokenless overload of an async method that offers a
`CancellationToken` overload silently drops cancellation: the operation can't be
aborted when the user cancels, the app shuts down, or a timeout fires — work
keeps running, resources stay held, and shutdown hangs.

## Do this
1. Find the ambient token — the method's own `CancellationToken` parameter,
   `HttpContext.RequestAborted`, or the host's shutdown token — and pass it to
   the overload.
2. If no token is in scope, add a `CancellationToken` parameter (usually
   optional, defaulting to `default`) and thread it through from the caller.
3. Check the rest of the call chain in the same method: one forwarded token
   usually reveals several other tokenless calls worth fixing.

## AVOID
- Do not pass `CancellationToken.None` just to reach the overload — that
   compiles, silences the rule, and preserves the exact bug: nothing can
   cancel the operation.
- Do not add a token parameter and then ignore it inside the method; thread it
   to the actual async calls.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
