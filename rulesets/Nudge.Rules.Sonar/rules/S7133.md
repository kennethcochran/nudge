# S7133 — Locks should be released within the same method

## Why
A lock acquired in one method and released in another — or on only some
code paths — is an abandonment waiting to happen: an exception between
acquire and release, or one forgotten release call, deadlocks every later
contender. This rule flags Monitor.Enter / mutex / semaphore acquisitions
whose release isn't in the same method.

## Do this
1. Use the lock statement (or SemaphoreSlim with try/finally in the same method) so acquisition and release are lexically paired.
2. If you must call Monitor.Enter directly, pair it with Monitor.Exit in a finally block in the same method — covering every return and every exception path.
3. Search for the same acquire-elsewhere-release pattern in neighboring code; it rarely appears only once.

## AVOID
- Do not add the missing Exit/Release in a different method or in the caller — the pairing stays invisible and the next refactor drops one side.
- Do not rely on Dispose or a finalizer to release the lock; lock lifetime must be scoped, not tied to object lifetime.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
