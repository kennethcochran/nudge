# S1048 — Finalizers should not throw exceptions

## Why
An exception escaping a finalizer (destructor) terminates the process — the CLR
treats it as unrecoverable. Finalizers run on the GC thread at unpredictable
times, when the object graph may already be torn down; throwing there turns a
cleanup path into a crash, and the original error information is lost with it.

## Do this
1. Make the finalizer exception-proof: wrap the body in try/catch and swallow
   (or safely log) everything — a finalizer is a context where failure is not
   an option.
2. Better: move cleanup into the `Dispose(bool)` pattern so the finalizer only
   runs as a last resort, and keep the finalizer body trivial.
3. Never call throwing methods from a finalizer; audit every call in the
   finalizer's path.

## AVOID
- Do not move the throwing code into a private helper called by the finalizer
   and claim the finalizer "doesn't throw" — the exception still escapes from
   the finalizer's call stack and still kills the process.
- Do not catch-and-rethrow (`catch { throw; }`) to "log" the failure;
   rethrowing from a finalizer is still process termination.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
