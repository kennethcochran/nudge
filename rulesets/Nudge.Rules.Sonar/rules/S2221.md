# S2221 — "Exception" should not be caught

## Why
`catch (Exception)` swallows everything indiscriminately — I/O failures, out of
memory, fatal runtime errors — usually followed by log-and-continue as if
nothing happened. Real failures get buried and the program limps on in a
corrupted state instead of failing fast where the problem is diagnosable.

## Do this
1. Catch the specific exception types the code can actually handle
   (`IOException`, `TimeoutException`, ...).
2. If you genuinely need a last-resort boundary (top of a worker loop, request
   pipeline), catch broadly but only to log and fail the operation — never to
   resume normal flow silently; rethrow what you can't handle.
3. Delete empty `catch (Exception) {}` blocks entirely; they are pure
   information destruction.

## AVOID
- Do not catch `Exception` and immediately `throw;` with nothing in between —
   the catch block does nothing; delete it.
- Do not dodge by spelling it `System.Exception` through an alias or catching a
   base type under another name; the rule targets the breadth of the catch,
   not the spelling.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
