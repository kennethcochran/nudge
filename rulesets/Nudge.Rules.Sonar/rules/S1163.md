# S1163 — Exceptions should not be thrown in finally blocks

## Why
A `throw` inside `finally` replaces any exception already in flight from the
`try` — the original error (the one that explains what actually went wrong)
is silently discarded, and the stack trace points at cleanup code instead of
the failure. It's CRITICAL because it destroys the single most useful
debugging artifact you have.

## Do this
1. Move the throwing logic out of the `finally`: do the fallible work
   before the `try`, or handle the outcome after it.
2. If the finally must attempt something that can fail (e.g. closing a flaky
   resource), catch and log inside the finally instead of throwing —
   cleanup failures shouldn't mask business-logic failures.
3. If both the try and the cleanup can fail and both matter, capture the
   cleanup failure and surface it *after* the finally — e.g. attached as an
   inner exception on an exception thrown outside the block.

## AVOID
- Do not wrap the finally's throw in a nested try/catch that rethrows — the
  masking behavior is identical, just indented.
- Do not "fix" it by throwing from inside the finally with the original
  attached as `InnerException`; the in-flight exception is still replaced
  and its stack context lost.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
