# S6668 — Logging arguments should be passed to the correct parameter

## Why
Logging frameworks give exceptions their own parameter for a reason:
_logger.LogError(ex, "failed") preserves the stack trace and lets sinks
render it structurally, while _logger.LogError("failed {Ex}", ex) flattens
the exception into the message text and loses the stack to structured sinks.
This rule flags exception values passed as ordinary message arguments.

## Do this
1. Move the exception to the dedicated parameter: _logger.LogError(ex, "message with {Placeholders}", args).
2. Keep the message template static with named placeholders — don't interpolate values into it.
3. Check neighboring log calls; the pattern is usually copy-pasted.

## AVOID
- Do not interpolate the exception into the message ($"failed: {ex}") — that is exactly the flattening the rule complains about, and the stack trace is still lost to structured sinks.
- Do not pass the exception twice, once as an argument and once as the dedicated parameter; use the dedicated parameter.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
