# S2245 — Pseudorandom number generators (PRNGs) should not be used in security contexts

## Why
`System.Random` is deterministic and seeded from the clock — an attacker who
observes a few outputs can predict the rest. Using it for tokens,
password-reset codes, salts, nonces, or session IDs makes those secrets
guessable, which collapses whatever security was built on top of them.

## Do this
1. Confirm the flagged use is security-sensitive (token, nonce, salt, key
   material, reset code) rather than benign (test data, procedural
   generation).
2. Replace `new Random()` with
   `System.Security.Cryptography.RandomNumberGenerator`
   (`RandomNumberGenerator.GetBytes(...)` / `GetInt32(...)`).
3. If both security and non-security randomness exist nearby, leave a comment
   marking which is which so the next reader doesn't "simplify" them together.
4. Re-run the tests covering that path.

## AVOID
- Do not keep `Random` and just "reseed better" (seeding from `Guid`,
   `DateTime.Ticks`, or a hash) — it is still not a CSPRNG and its output
   stays predictable. Use `RandomNumberGenerator`.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
