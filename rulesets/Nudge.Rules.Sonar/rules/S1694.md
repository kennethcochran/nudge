# S1694 — An abstract class should have both abstract and concrete methods

## Why
An abstract class with only abstract members is an interface wearing a costume:
it forces single-inheritance consumption for no benefit, since callers get
polymorphism either way. An abstract class with no abstract members at all can't
be meaningfully extended — subclasses inherit behavior but define none of their
own. The rule pushes the design toward whichever construct actually fits.

## Do this
1. If every member is abstract, convert the type to an `interface` — callers
   keep polymorphism and gain the freedom of multiple interface
   implementation.
2. If no member is abstract, either make it a concrete class or introduce the
   genuinely abstract members that subclasses are supposed to define.
3. Update implementers and call sites for the new shape, then rebuild and run
   the tests.

## AVOID
- Do not add a token abstract method (or a token concrete helper) just to
   satisfy the ratio — a fake member that exists only for the analyzer is
   worse than the smell. Pick the construct (interface, abstract class, or
   concrete class) that the design actually wants.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
