# S6961 — API Controllers should derive from ControllerBase instead of Controller

## Why
`Controller` extends `ControllerBase` with view support (`View()`,
`ViewBag`, view discovery) — dead weight in an API controller that only
returns data. Deriving API controllers from `Controller` drags the MVC view
pipeline into the inheritance chain and confuses readers about whether the
controller serves pages; in some configurations it also changes behavior
(view-location expansion, temp data).

## Do this
1. Change the base class from `Controller` to `ControllerBase`.
2. Confirm nothing in the controller uses view features (`View()`,
   `PartialView()`, `ViewBag`/`ViewData`); if something does, it's not an
   API controller — move that action to a real MVC controller instead of
   keeping the wrong base.
3. Keep `[ApiController]` and routing attributes as they are; they work
   identically on `ControllerBase`.

## AVOID
- Do not keep `Controller` and just avoid calling view methods — the wrong
  base still advertises view capability to every future editor.
- Do not "fix" it by removing the base class entirely and reimplementing
  `ControllerBase` behavior by hand.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
