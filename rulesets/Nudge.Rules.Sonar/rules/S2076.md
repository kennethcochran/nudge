# S2076 — OS commands should not be vulnerable to command injection attacks

## Why
The rule fires when user-controlled data flows into `Process.Start` (or
similar) as the executable name or an argument string. When
`UseShellExecute` is true, or arguments are passed as one concatenated
string, metacharacters (`;`, `&`, `|`, backticks) in the input can escape the
intended command and run an attacker's command with your process's
privileges. This is a BLOCKER because a single unsanitized textbox can mean
full remote code execution on the host.

## Do this
1. Pass arguments through `ProcessStartInfo.ArgumentList` — one entry per
   argument — instead of a single concatenated string. This bypasses shell
   parsing entirely.
2. Set `UseShellExecute = false` unless you specifically need shell behavior,
   and validate the executable path against an allow-list of known tools.
3. Constrain the user input itself: accept only allow-listed values or
   strictly validate the format before use.

## AVOID
- Do not "fix" it by wrapping the input in quotes — quote-breaking
  (`" & evil`) is a classic, well-documented bypass.
- Do not blacklist a few characters (`;`, `&`) and declare victory;
  blocklists miss encodings, quoting tricks, and shell-specific
  metacharacters.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
