# S4211 — Members should not have conflicting transparency annotations

## Why
The .NET transparency model (SecurityCritical / SecuritySafeCritical /
SecurityTransparent) decides which code may call into what. A member whose
annotation conflicts with the contract member it overrides or implements
creates a hole: partially trusted callers can reach critical code through the
mismatched slot. This rule flags members with conflicting transparency
annotations.

## Do this
1. Walk the inheritance and interface chain and make the annotation consistent — an override must be at least as critical as the member it overrides.
2. If the member genuinely must be callable from transparent code, mark it SecuritySafeCritical and audit exactly what it touches — do not widen the hole any further than the requirement.
3. Where the project targets .NET Core or later and the model is vestigial, removing the annotations can be legitimate — but do it as a deliberate cleanup of the whole hierarchy, not as spot deletions to silence findings.

## AVOID
- Do not stamp [SecuritySafeCritical] on every flagged member to make the conflicts disappear — that is the analyzer equivalent of chmod 777; each annotation must reflect the member's actual trust requirement.
- Do not remove the base member's annotation while overrides still assume it; fix the chain, not one link.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
