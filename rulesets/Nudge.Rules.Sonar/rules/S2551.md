# S2551 — Shared resources should not be used for locking

## Why
`lock(this)`, `lock(typeof(X))`, `lock("name")`, or locking any publicly
reachable object lets unrelated code take the *same* lock — a string literal
is interned process-wide, so `lock("sync")` in your class contends with
`lock("sync")` anywhere else in the process. The result is deadlocks and
lock convoys caused by code you can't see.

## Do this
1. Add a dedicated lock object: `private readonly object _sync = new();`
2. Lock on that object and nothing else.
3. Audit the class for `lock(this)`, `lock(typeof(...))`, and `lock("...")`
   and replace each one.

## AVOID
- Do not lock on a different *public* object per call site "to reduce
  contention" — the fix is a private dedicated lock object, not a reshuffled
  public one that strangers can still grab.
- Do not lock on a `Type` or a boxed value type — same shared-identity
  problem, less obvious spelling.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
