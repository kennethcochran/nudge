# S4057 — Locales should be set for data types

## Why
`new DataTable()` and `new DataSet()` default their `Locale` to the
machine's current culture. String sorting, comparison, and casing inside
the table then depend on where the code runs: data written to a database
or file on one machine can sort or compare differently when read on
another. For data that is stored, shared, or compared across machines,
the locale must be chosen deliberately — ordinarily the invariant culture.

## Do this
1. Set `table.Locale = CultureInfo.InvariantCulture` (or the specific
   culture the data belongs to) immediately after creating each
   `DataTable` / `DataSet` that holds shared or persisted data.
2. Audit existing tables: any `DataTable` / `DataSet` without an explicit
   `Locale` is making an implicit bet on the deployment machine's culture.

## AVOID
- Do not set `Locale = CultureInfo.CurrentCulture` to "make it explicit".
  That spells out the ambient default without changing it — the behavior
  still varies by machine. Choose the locale deliberately.
- Do not try to fix this by setting the thread's culture instead — that's
  global mutable state affecting every culture-sensitive operation in the
  process, not a decision about this data.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
