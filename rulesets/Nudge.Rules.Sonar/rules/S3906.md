# S3906 — Event Handlers should have the correct signature

## Why
The .NET convention — `void Handler(object sender, EventArgs e)` — is what
delegate compatibility, designer-generated wiring, and every reader expect.
A handler with the wrong parameter types or a non-void return breaks
subscription, confuses tooling, and forces every subscriber to adapt to one
rebel method.

## Do this
1. Change the handler to `(object? sender, EventArgs e)` — or the specific
   `EventArgs` subclass the event uses — returning `void`.
2. If the handler needs extra data, derive a custom `EventArgs` type rather
   than widening the signature.

## AVOID
- Do not adapt at each subscription site with a lambda wrapper
  (`+= (s, e) => handler(e)`). That multiplies the workaround by the number
  of subscribers — fix the handler once.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
