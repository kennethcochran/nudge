# S6585 — Don't hardcode the format when turning dates and times to strings

## Why
A hardcoded format like `"dd/MM/yyyy"` bakes one culture's convention into the
code: under a different `CurrentCulture` the same format string parses and
prints differently, and month/day order silently swaps. Date handling that
depends on the ambient culture is a localization bug waiting for a user in
another locale.

## Do this
1. Use standard format specifiers (`"d"`, `"o"`, `"u"`) that adapt to the
   current culture for user-facing output.
2. When a fixed wire or storage format is genuinely required, pass
   `CultureInfo.InvariantCulture` explicitly.
3. Parse with `TryParseExact` using the *same* explicit culture and format you
   wrote with — symmetry between writer and reader.

## AVOID
- Do not switch the hardcoded string to `"MM/dd/yyyy"` "for the US users" —
  that is the same bug with a different home team; culture must be explicit,
  not assumed.
- Do not sprinkle `CultureInfo.CurrentCulture` explicitly everywhere as the
  "fix" — the ambient culture is still ambient; the point is to decide
  deliberately per call site.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
