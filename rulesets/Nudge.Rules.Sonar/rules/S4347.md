# S4347 — Secure random number generators should not output predictable values

## Why
System.Random is a deterministic PRNG: its output is fully determined by
the seed, and the parameterless seed comes from the clock. Tokens,
password-reset links, salts, IVs, or nonces drawn from it can be reconstructed
by an attacker who guesses the seed window. This rule flags predictable
generators used for security-sensitive values.

## Do this
1. Replace System.Random with System.Security.Cryptography.RandomNumberGenerator (GetBytes / GetInt32) for anything security-sensitive.
2. Audit every call site of the replaced generator — tokens, salts, session IDs — not just the one the diagnostic points at.
3. Keep System.Random only for non-security uses (shuffling UI, games, simulations) and name the variable so the next reader knows it is not cryptographic.

## AVOID
- Do not seed Random with Guid.NewGuid().GetHashCode(), Environment.TickCount, or DateTime.Now.Ticks to 'make it unpredictable' — the stream stays deterministic and the seed space stays enumerable.
- Do not create a new Random() per call; instances created in rapid succession share the same clock seed and emit identical sequences.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
