# S4830 — Server certificates should be verified during SSL/TLS connections

## Why
A `ServerCertificateCustomValidationCallback` that returns `true` — or ignores
`SslPolicyErrors` — makes TLS decorative: any man-in-the-middle with a
self-signed certificate can read and modify the traffic. Certificate
validation is the only thing distinguishing your server from an impostor.

## Do this
1. Delete the custom validation callback entirely and let the platform perform
   full chain and hostname validation.
2. If you must customize (private CA, certificate pinning), verify the chain
   and the hostname yourself inside the callback and return `false` for
   anything else — never a blanket `true`.
3. Treat any "temporary" bypass as a blocking issue: search the codebase for
   other callbacks with the same shape.

## AVOID
- Do not return `true` "temporarily" with a TODO comment — temporary bypasses
  ship, and the TODO outlives everyone's memory of it.
- Do not log the validation error and continue anyway ("we log it, so it's
  fine") — logging an accepted forgery is the same vulnerability with
  paperwork.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
