# S3776 — Cognitive Complexity Too High

## Why
Cognitive Complexity measures how hard a method is to *understand*, not just how
long it is: nesting, branches, and jumps each add cost. A method scoring over the
threshold is hard to review, hard to test (every path needs a case), and where bugs
hide — in a compiler, a misunderstood optimization pass is a miscompile waiting to
happen. The number is a proxy for "a reader can't hold this in their head."

## Do this
1. Identify the distinct *jobs* the method is doing. Extract each job into its own
   method with a name that says what it computes — the extraction should make the
   original method read as a short sequence of named steps.
2. Replace nested conditionals with early returns / guard clauses where the logic
   allows; flattening genuinely reduces the reader's burden.
3. After refactoring, re-run the build: the score should drop because the method
   got simpler, and the new methods should each be independently testable.

## AVOID
- Do not split the method into helpers *solely* to lower the number while keeping
  the same tangled logic — e.g. moving a nested branch verbatim into a
  `DoBranchStuff()` helper. The score drops, the code is no simpler, and you have
  now hidden the complexity behind a meaningless name. This is the single most
  common way agents game this rule, and it makes the code worse.
- Do not "simplify" by collapsing distinct cases into clever boolean expressions.
  Trading branches for unreadable predicates keeps the score low and the confusion
  high.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`, and do not
  raise the threshold in `.editorconfig` to make the warning go away. Suppression
  of analyzer diagnostics is forbidden by the project's AGENTS.md.
