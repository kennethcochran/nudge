# S4507 — Debugging features should not be enabled in production

## Why
Debugging aids — `Debugger.Break()`/`Debugger.Launch()` calls, debug-only
endpoints, verbose diagnostic pages, detailed stack traces served to clients —
are written for a developer's eyes. In production they leak internals, stall a
process waiting for a debugger that never attaches, or hand an attacker a
working introspection tool.

## Do this
1. Find the flagged debugging feature and ask whether it has any legitimate
   production purpose — usually it doesn't.
2. Delete it outright (a `Debugger.Break()` left from a debugging session, a
   `/debug` endpoint) rather than leaving it dormant.
3. If a diagnostic is genuinely needed in production (health checks, structured
   logs), rebuild it as a production feature: minimal output, no internals,
   behind authentication.
4. Verify the release build and pipeline have no debug switches flipped on
   (debug compilation flags, development exception pages).

## AVOID
- Do not just hide the debugging feature behind a configuration flag that
   production can still turn on — the feature and its risks remain one
   misconfiguration away.
- Do not move a `Debugger.Break()` into a helper method to get it off the
   flagged line; the process still halts waiting for a debugger.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
