# S2699 — Tests should include assertions

## Why
A test that never asserts passes vacuously — it exercises code but verifies
nothing, so regressions sail through green. It's worse than no test: it spends
CI time while claiming coverage of behavior it doesn't check.

## Do this
1. Decide what behavior the test is pinning down, then assert it: return
   values, state changes, thrown exceptions (`Assert.Throws`), or mock
   verifications.
2. If the test only checks "doesn't throw", say so explicitly with
   `Assert.DoesNotThrow` (or your framework's equivalent) so the intent is
   visible.
3. Delete the test if there's genuinely nothing to assert — a placeholder with
   a TODO is honest; a silent pass is not.

## AVOID
- Do not "fix" it with `Assert.True(true)`, `Assert.Pass()`, or
  `Assert.That(true)` — a tautological assertion verifies nothing and exists
  only to fool the rule.
- Do not assert on the test's own setup (`Assert.NotNull(fixture)`) as the
  sole assertion — that tests your arrange block, not the code under test.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
