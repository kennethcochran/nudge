# S5131 — Endpoints should not be vulnerable to reflected cross-site scripting (XSS) attacks

## Why
Reflected XSS happens when an endpoint takes attacker-controlled input (a query
string, form field, or route value) and echoes it into the response HTML without
encoding. The victim's browser then executes the injected script in the site's
origin — session hijacking, credential theft, actions performed as the victim.
In ASP.NET Core, Razor's `@` output is HTML-encoded by default, but
`@Html.Raw(...)`, hand-built HTML strings, and `Content(html)` bypass that
protection entirely.

## Do this
1. Trace the flagged flow: find where untrusted input reaches the response
   body.
2. Encode at the output, in the matching context: use Razor `@` interpolation
   (auto-encoded) instead of `@Html.Raw`, or
   `System.Text.Encodings.Web.HtmlEncoder.Default.Encode(...)` when building
   strings manually.
3. If the endpoint must render HTML supplied by the user, sanitize it with a
   whitelist sanitizer (e.g. `HtmlSanitizer`), never with string replacement.
4. Add a regression test that posts a `<script>` payload and asserts the
   response contains the encoded form, not live markup.

## AVOID
- Do not "fix" it by stripping `<script>` tags with `string.Replace` — blocklist
  filtering is trivially bypassed (event-handler attributes, SVG, malformed
  markup, encodings). Encode output or whitelist-sanitize.
- Do not move the untrusted value into a different sink (a JSON blob embedded
  in the page, an attribute value) without encoding for *that* context —
  HTML-encoding does not protect a JavaScript string literal.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
