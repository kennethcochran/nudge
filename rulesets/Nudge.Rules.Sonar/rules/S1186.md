# S1186 — Empty Method

## Why
An empty method is a lie in the codebase: its name promises behavior and
delivers none. Callers assume the call does something — cache invalidation,
event notification, cleanup — and write code on that assumption. When the
assumption is wrong, the bug is invisible at the call site. Either the method
should do what its name says, or it shouldn't exist.

## Do this
1. If the method is a stub for planned behavior, implement it now — the
   name is a specification, honor it.
2. If the behavior genuinely isn't needed, delete the method and its call
   sites. Dead surface area is a liability.
3. If it's an intentional no-op (e.g. a base-class hook), say so: a comment
   explaining *why* it's empty, or make it clear in the name.

## AVOID
- Do not add a meaningless body (`;`, `return;`, a no-op statement) just to
  make the method non-empty. An empty method with a semicolon in it is still
  an empty method — you've silenced the detector, not fixed the lie.
- Do not add `throw new NotImplementedException()` as a permanent state.
  That's a stub marker, not an implementation; it just converts a silent
  lie into a runtime crash.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
