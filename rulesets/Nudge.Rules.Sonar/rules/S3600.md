# S3600 — "params" should not be introduced on overrides

## Why
Adding params to an override when the base method doesn't have it creates
a silent overload-resolution trap: calls through the base type don't get the
params expansion, calls through the derived type do — same name, different
calling conventions depending on the static type. This rule flags params
introduced on overrides.

## Do this
1. Move params to the virtual/base declaration so the whole hierarchy shares one calling convention, and keep overrides signature-identical to the base.
2. If the base is outside your control, don't add params on the override — add a separate overload or an extension method with the params form instead.
3. Check existing call sites for ones that were (or weren't) using params expansion through each static type.

## AVOID
- Do not silence it with 'new' to hide the base method — that fractures polymorphism: base-typed and derived-typed callers resolve to different methods entirely, which is worse than the params mismatch.
- Do not keep the params override and add a non-params overload that forwards; the resolution trap remains for every caller.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
