# S3998 — Threads should not lock on objects with weak identity

## Why
`lock` on a string literal, a boxed value, `this`, or a `Type` object
doesn't lock what you think: string literals are interned process-wide
(your lock is secretly global, shared with unrelated code locking the same
literal), boxed values create a *new* object per box (your lock protects
nothing), and `Type` / `this` expose the lock to outsiders who can deadlock
you. It's CRITICAL because the failure mode is Heisenbugs — deadlocks and
races that vanish under a debugger.

## Do this
1. Add a dedicated `private readonly object _lock = new();` field and lock
   on that — nothing else can see it, intern it, or box it.
2. Replace every `lock` on the weak-identity object with the new field,
   including locks in other methods guarding the same state.
3. Never lock on `this`, on string literals, or on publicly reachable
   objects; treat lock objects as private infrastructure.

## AVOID
- Do not "fix" it by locking on `new object()` created inside the method —
  a fresh object per call means no mutual exclusion at all; that's worse
  than the original bug.
- Do not switch to locking on another weak-identity object (a different
  string, a boxed int field); the rule names the category, not the
  instance.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
