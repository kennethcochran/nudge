# S5042 — Expanding archive files without controlling resource consumption is security-sensitive

## Why
A zip bomb is a few kilobytes of compressed data that expands to gigabytes —
all zeros compress almost infinitely. If your code extracts an untrusted archive
without bounding the total expanded size, the entry count, or the compression
ratio, a single malicious upload can fill the disk or exhaust memory and take
the process (or the machine) down. The archive library will happily do exactly
what you asked; the denial of service is in the missing guard, not the library.

## Do this
1. Before/during extraction, enforce hard limits: maximum total uncompressed
   bytes, maximum number of entries, and maximum compression ratio
   (uncompressed ÷ compressed size, e.g. 100:1).
2. Prefer streaming extraction entry-by-entry, accumulating a running total and
   aborting the moment a limit is exceeded — never buffer the whole archive
   in memory first.
3. Validate entry paths too (no `../` traversal), but path validation is a
   separate concern from resource exhaustion — do both.

## AVOID
- Do not "fix" this by catching `OutOfMemoryException` / `IOException` around
  the extraction. Catching the explosion is not preventing it — the disk may
  already be full and the process already doomed by the time you catch.
- Do not check only the compressed file size. A 42 KB bomb is 42 KB on disk
  and 4.5 GB expanded; the compressed size tells you nothing.
- Do not rely on a single entry-count limit without a byte limit (or vice
  versa) — a single entry can still be gigabytes.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
