# S4502 — CSRF protections should not be disabled

## Why
Antiforgery validation exists so that only your own pages can trigger
state-changing requests. Disabling it — removing the validation attribute,
suppressing antiforgery globally, or weakening cookie `SameSite` — lets any
site the victim visits forge requests with the victim's cookies, silently.
CSRF is invisible to the victim and the protection is cheap, so there is no
safe reason to turn it off.

## Do this
1. Re-enable antiforgery validation on every state-changing endpoint
   (POST/PUT/PATCH/DELETE).
2. For APIs consumed by browsers, issue and validate antiforgery tokens; for
   non-browser clients prefer cookie-independent authentication (e.g. bearer
   tokens), which is not subject to CSRF.
3. Keep `SameSite=Lax` (or `Strict`) on authentication cookies.

## AVOID
- Do not "fix" the diagnostic by switching the endpoint to GET. State
  changes over GET are still forgeable — an `<img>` tag is all it takes —
  so you have traded one vulnerability for another.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
