# S3881 — "IDisposable" should be implemented correctly

## Why
IDisposable has a canonical pattern for a reason: the protected virtual
Dispose(bool), the public Dispose() that calls it and suppresses finalization, and no resurrection of disposed state. Half-implementations leak — resources freed twice, finalizers running on disposed objects, derived classes unable to extend cleanup. This rule flags incorrect implementations.

## Do this
1. Implement the full pattern: public void Dispose() calls Dispose(true) then GC.SuppressFinalize(this); protected virtual void Dispose(bool disposing) releases managed resources only when disposing is true and unmanaged resources always; add a finalizer only if you directly hold unmanaged resources — prefer SafeHandle instead.
2. Make Dispose idempotent — disposing twice must be safe.
3. If the class is sealed and holds no unmanaged resources, the simplified pattern (Dispose + SuppressFinalize, no finalizer, no bool overload) is acceptable — but write it completely.

## AVOID
- Do not write an empty Dispose() to satisfy the interface — it pretends cleanup happens and guarantees the leak becomes someone else's problem.
- Do not throw NotImplementedException from Dispose; that is an empty Dispose() with extra steps.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
