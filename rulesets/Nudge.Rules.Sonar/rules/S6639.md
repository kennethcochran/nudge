# S6639 — Memory allocations should not be vulnerable to Denial of Service attacks

## Why
Allocating a buffer sized by untrusted input (`new byte[sizeFromRequest]`,
`Array.CreateInstance`, collection capacities) lets a single malicious request
force an `OutOfMemoryException` or crushing GC pressure. The allocation happens
before any later validation can help, so the size must be constrained *before*
the allocation.

## Do this
1. At the allocation site, trace where the size value comes from; if any source
   is user-controlled, that is the vulnerability.
2. Enforce a sane upper bound on the size *before* allocating, derived from
   what the operation legitimately needs (a documented max payload size), and
   reject the request above it.
3. Prefer streaming or chunked processing over materializing the whole payload
   when the size can legitimately be large.

## AVOID
- Do not wrap the allocation in `try/catch (OutOfMemoryException)`. Catching
  OOM is unreliable — the process may already be unrecoverable — and it leaves
  the attacker free to retry the attack indefinitely. Bound the size up front
  instead.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
