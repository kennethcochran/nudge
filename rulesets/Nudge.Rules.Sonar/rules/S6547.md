# S6547 — Environment variables should not be defined from untrusted input

## Why
Environment variables are inherited by every child process and consulted by the
runtime, the shell, and native libraries. If untrusted data flows into
`Environment.SetEnvironmentVariable` — the variable *name* or its *value* — an
attacker can hijack behavior: a poisoned `PATH` redirects process launches,
`LD_PRELOAD`/`DYLD_INSERT_LIBRARIES` inject native code, proxy variables reroute
traffic. The rule fires when outside input reaches an environment-variable
definition.

## Do this
1. Trace the flagged call back to its source: request input, CLI args, config
   files, or anything else external.
2. If the variable must be set, restrict the *name* to a fixed allowlist of
   names your code owns, and validate the *value* against what is allowed
   (reject path separators, null bytes, unexpected characters).
3. Prefer not to use environment variables as the channel at all: pass the data
   as an explicit method argument, a config object, or a command-line argument
   to the child process.
4. If a child process needs the value, set it on that process's
   `StartInfo.Environment` rather than the process-wide environment.

## AVOID
- Do not "sanitize" by stripping only the one dangerous character you thought
  of (removing `;` but leaving `:` or null bytes, for example). Validate
  against what is allowed, not what you remembered to forbid.
- Do not fix the value while leaving the variable *name* attacker-controlled —
  a hostile name with a clean value is still hostile, and vice versa.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
