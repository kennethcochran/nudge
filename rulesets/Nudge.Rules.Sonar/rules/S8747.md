# S8747 — Migrations should not narrow column types without converting existing data

## Why
A migration that shrinks a column — shorter string length, smaller decimal
precision — runs against a database that already has rows. Existing values
that no longer fit get silently truncated or make the migration fail, so
deploying the migration destroys or blocks on production data.

## Do this
1. In the migration, add an explicit data-conversion step (UPDATE) that
   brings existing rows within the new type's range before the `AlterColumn`.
2. Reconsider whether narrowing is needed at all — widening is always safe.
3. Test the migration against a realistic data snapshot, not an empty
   database.

## AVOID
- Do not dodge the diagnostic by replacing `AlterColumn` with drop-column
  plus add-column. That deletes the existing data instead of truncating it —
  the same data loss, louder.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
