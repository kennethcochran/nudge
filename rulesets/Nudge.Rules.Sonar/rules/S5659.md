# S5659 — JWT should be signed and verified with strong cipher algorithms

## Why
A JWT signed with a weak algorithm — or `alg: none` — lets an attacker forge
tokens. The classic break is algorithm confusion: the validator is tricked into
verifying an RS256 token as HMAC using the public key as the secret. The rule
flags token creation and validation configured with weak or mismatched
algorithms.

## Do this
1. Sign with a strong algorithm — HS256 minimum with a 256-bit+ random key, or
   RS256/ES256 with proper key management — and configure validation to accept
   only that algorithm (pin `ValidAlgorithms`, set `IssuerSigningKey` with
   `ValidateIssuerSigningKey`).
2. Never accept `alg: none`, and never let the token's header choose the
   algorithm — pin the expected algorithm server-side in the validator.
3. Keep keys in a real secret store, rotate them, and tag each with a `kid`
   so rotation doesn't break validation.

## AVOID
- Do not "fix" it by changing the `alg` header string while the validation
  code still accepts whatever the token claims — pin the algorithm in the
  validator, not in the token.
- Do not set `RequireSignedTokens = false` to make a failing test pass —
  that's deleting the signature check, not strengthening it.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
