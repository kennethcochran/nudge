# CS0659 — Override Equals Without GetHashCode

## Why
`Equals` and `GetHashCode` are a contract: equal objects must produce equal
hash codes. If you override `Equals` but inherit `object.GetHashCode` (which
is identity-based), two objects that compare equal will hash differently.
Put them in a `Dictionary` or `HashSet` and lookups silently fail — the
collection can't find an object it demonstrably contains. This is one of the
most common sources of "impossible" collection bugs.

## Do this
1. Override `GetHashCode` to combine the same fields `Equals` compares,
   e.g. `HashCode.Combine(X, Y)`.
2. The two methods must agree: if `Equals` says two instances are equal,
   `GetHashCode` must return the same value for both. Test this property
   directly.
3. If the type is a simple value carrier, consider a `record` instead —
   the compiler generates both correctly.

## AVOID
- Do not implement `GetHashCode() => 0;` (or any constant). It satisfies the
  letter of the rule — equal objects hash equally — but destroys hash
  distribution: every instance lands in one bucket and lookups degrade to
  linear scans. This is the classic metric-gaming move for this rule.
- Do not hash a different set of fields than `Equals` compares. The contract
  is about agreement between the two methods.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
