# S5135 — Deserialization should not be vulnerable to injection attacks

## Why
Type-resolving deserializers (BinaryFormatter, NetDataContractSerializer, or JSON
with type-name handling enabled) instantiate .NET types named by the payload
itself. A crafted byte stream can therefore name gadget types that run code
during construction or property setting — remote code execution without any bug
in your own code, only a reachable deserialization call. This rule fires when
such a deserializer is fed data that can originate outside the process.

## Do this
1. Stop feeding untrusted data to type-resolving deserializers. Prefer System.Text.Json with default options (no polymorphic type discriminators) or another format that cannot instantiate arbitrary types.
2. If a legacy formatter cannot be removed yet, constrain it with a SerializationBinder allow-list of exactly the expected types — treat that as containment, not a fix, and plan the migration.
3. Validate the payload before deserializing: authenticated origin, schema-checked shape, and reject anything unexpected rather than best-effort parsing it.

## AVOID
- Do not swap BinaryFormatter for Newtonsoft.Json with TypeNameHandling.All, or a custom SerializationBinder that allows everything — the gadget chain survives the rename.
- Do not wrap the call in try/catch and retry with looser settings on failure; the malicious payload still gets parsed.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
