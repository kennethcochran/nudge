# S6549 — Accessing files should not lead to filesystem oracle attacks

## Why
When any part of a file path comes from user input, branching on
`File.Exists`/`Directory.Exists` — or letting "not found" and "access denied"
produce observably different behavior — hands the attacker a yes/no oracle for
probing your filesystem. The existence check also introduces a time-of-check /
time-of-use race: the file can change between the check and the operation.

## Do this
1. Stop gating behavior on `File.Exists` / `Directory.Exists` for
   user-influenced paths.
2. Confine the name under a fixed base directory: resolve with
   `Path.GetFullPath(Path.Combine(baseDir, name))` and reject the result unless
   it starts with the base directory (this also blocks `../` traversal).
3. Attempt the operation directly and catch the specific exceptions
   (`FileNotFoundException`, `UnauthorizedAccessException`), returning one
   generic failure that does not distinguish "missing" from "forbidden".

## AVOID
- Do not "fix" the oracle by catching every exception and then re-checking
  existence to pick a friendlier message — different messages per outcome are
  still an oracle.
- Do not rely on cosmetic normalization (trimming, lowercasing, hashing the
  path) while still branching on attacker-influenced input; the branch is the
  leak, not the formatting.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
