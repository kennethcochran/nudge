# S3346 — Expressions used in "Debug.Assert" should not produce side effects

## Why
Debug.Assert calls are removed from Release builds — any side effect inside
the asserted expression (incrementing a counter, advancing an enumerator,
mutating state) silently stops happening in production, so Debug and Release
behave differently. This rule flags asserted expressions with side effects.

## Do this
1. Hoist the side effect out of the assert: execute it into a local first, then assert on the local — e.g. var n = Advance(); Debug.Assert(n == expected);.
2. Verify the method's behavior no longer depends on whether DEBUG is defined.
3. Re-check the other asserts in the same method; the pattern tends to repeat.

## AVOID
- Do not extract the expression into a helper that still performs the side effect and returns its result to the assert — the call (and its side effect) is still compiled out in Release.
- Do not switch Debug.Assert to Trace.Assert to keep the side effect running; that makes production behavior depend on an assertion mechanism.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
