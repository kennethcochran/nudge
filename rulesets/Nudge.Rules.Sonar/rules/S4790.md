# S4790 — Weak hashing algorithms should not be used

## Why
MD5 and SHA-1 are broken for security purposes: practical
collision attacks exist for both, so they cannot be trusted for
integrity checks, signatures, tokens, or anything an attacker has an
incentive to forge. Using them in security-adjacent code is a
vulnerability even if no exploit is visible today.

## Do this
1. Identify what the hash is protecting. For passwords or key
   derivation, use a proper KDF: PBKDF2 (`Rfc2898DeriveBytes`), bcrypt,
   or Argon2 — never a fast general hash.
2. For integrity/fingerprinting, use SHA-256, SHA-384, SHA-512, or
   SHA-3.
3. If MD5/SHA-1 appears for a genuinely non-security purpose (e.g. a
   non-adversarial checksum for cache keys), document that explicitly at
   the call site — but re-check: "non-security" claims about hashes age
   badly.

## AVOID
- Do not replace MD5 with SHA-1 — it is flagged too, and equally
  broken for security use.
- Do not wrap the weak algorithm in a helper with a reassuring name
  (`HashSecurely`) — the algorithm is the problem, not the call site.

- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`. Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
