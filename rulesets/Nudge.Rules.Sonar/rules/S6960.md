# S6960 — Controllers should not have mixed responsibilities

## Why
A single controller serving unrelated resources — users, orders, and reports
in one class — becomes a god class: merge conflicts on every change, unclear
ownership, routing sprawl, and authorization rules that can't be reasoned about
per resource.

## Do this
1. Group the actions by resource or domain concept.
2. Split into one controller per resource (`UsersController`,
   `OrdersController`), each with its own route prefix.
3. Extract genuinely shared behavior into services, action filters, or
   authorization policies — not into a base controller class that re-creates
   the mixing one level up.

## AVOID
- Do not rename the controller to something vaguer (`DataController`,
  `MiscController`) to excuse the mix — the responsibility split is the fix,
  not the label.
- Do not "split" by moving actions into partial class files of the same
  controller — one class in three files is still one class.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
