# S2166 — Classes named like "Exception" should extend "Exception" or a subclass

## Why
A class named `FooException` that doesn't derive from `Exception` breaks the
one naming convention .NET enforces by culture: the `Exception` suffix
promises `catch (Exception)` will catch it and that it carries a stack
trace, `Message`, and `InnerException`. Code that catches by the name's
promise and code that throws it as a value will disagree at runtime.

## Do this
1. If the type represents an error, derive it from `Exception` (or a more
   specific built-in like `InvalidOperationException`) and add the standard
   constructors.
2. If it's not an error at all (a result type, a status wrapper), rename it
   to drop the `Exception` suffix — the name was the lie, not the
   hierarchy.
3. Update `catch` / `throw` sites and any serialization that referenced the
   old shape.

## AVOID
- Do not keep the non-Exception class and add `Message`- / `StackTrace`-
  shaped properties to "look like" an exception — duck-typing an exception
  defeats `catch` blocks and every diagnostic tool.
- Do not rename it to something like `FooError` while still throwing it
  with `throw` — only `Exception`-derived types can be thrown; the rename
  has to match the actual usage.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
