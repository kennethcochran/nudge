# S2257 — Custom cryptographic algorithms should not be used

## Why
The flagged class implements its own cipher, hash, or MAC. Hand-rolled crypto has not survived cryptanalysis: subtle flaws like biased output or weak diffusion are invisible to unit tests but exploitable in practice, and every reviewer must now audit an algorithm instead of a call site.

## Do this
1. Delete the custom implementation and use the platform primitives (`System.Security.Cryptography`: `Aes`, `SHA256`, `HMACSHA256`, `RSA`, `ECDsa`).
2. For password storage use a dedicated password hasher (PBKDF2 via `Rfc2898DeriveBytes`, BCrypt, or Argon2) — never a general-purpose hash.
3. If the class is only a thin, well-tested wrapper around a vetted primitive, restructure/rename it so it no longer presents as a novel algorithm.

## AVOID
- Do not rename the class to `AesWrapper` while keeping the custom math — renaming doesn't make it vetted.
- Do not add a comment claiming the algorithm is safe because it's proprietary — obscurity is not security.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
