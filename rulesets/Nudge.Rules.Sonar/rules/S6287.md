# S6287 — Applications should not create session cookies from untrusted input

## Why
A session cookie whose name or value is derived from user input (query string,
form field, header) enables session-fixation attacks: the attacker chooses the
victim's session identifier up front and then hijacks the authenticated
session. The danger is attacker *control* of the identifier, so the fix must
remove that control entirely, not clean the input.

## Do this
1. Generate the session identifier server-side with `RandomNumberGenerator`
   (never from request data) at the point the session is created.
2. Trace the flagged call site for any request-derived value flowing into the
   cookie's name or value and remove that flow completely.
3. When you create the cookie, mark it `HttpOnly`, `Secure`, and an
   appropriate `SameSite` mode.

## AVOID
- Do not "sanitize" the untrusted input (trim it, URL-encode it, strip special
  characters) and keep using it as the session value. Sanitizing leaves the
  attacker choosing the session identifier; only a server-generated random
  value removes their control.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
