# CS0162 — Unreachable Code Detected

## Why
Code after a `return`, `throw`, or `break` never executes. It's worse than
dead weight: a reader assumes every statement in a method runs, so unreachable
statements actively mislead about what the method does. Usually it's a fossil
from a refactor — the logic moved but the corpse stayed behind.

## Do this
1. Delete the unreachable statements. They're not coming back; that's what
   version control is for.
2. If the unreachable code looks like it was *meant* to run, the control
   flow above it is wrong — fix the `return`/`throw` placement, don't just
   delete the symptom.
3. Re-read the method after the fix: it should now say exactly what it does,
   no more.

## AVOID
- Do not "reach" the code by wrapping it in `if (false)` or similar tricks.
  It's still dead; you've just made the control flow lie about it.
- Do not move unreachable code into a helper method to hide it from the
  detector. Dead code in a new location is still dead code.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
