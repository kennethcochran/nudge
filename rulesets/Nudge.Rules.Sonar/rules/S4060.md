# S4060 — Non-abstract attributes should be sealed

## Why
Attribute classes are instantiated by the runtime via reflection, where
virtual dispatch surprises are hardest to debug — and an unsealed attribute
invites subclasses that silently change attribute semantics for every
consumer doing `GetCustomAttribute<BaseAttribute>()`. If inheritance isn't a
designed feature, close it.

## Do this
1. Add `sealed` to the attribute class.
2. If inheritance is a genuine design — a family of related attributes —
   make the base class `abstract` instead.
3. Before sealing, verify no external subclasses exist (search the solution
   and any consuming assemblies you own).

## AVOID
- Do not seal the class but leave a `protected` constructor "just in case" —
  a sealed class with a protected constructor is contradictory; make the
  constructor private.
- Do not "fix" it by making the attribute `abstract` when it was meant to be
  instantiated — abstract is for designed inheritance hierarchies, not a
  synonym for sealed.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
