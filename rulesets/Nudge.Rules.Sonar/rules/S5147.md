# S5147 — NoSQL operations should not be vulnerable to injection attacks

## Why
Building a NoSQL query by concatenating user input — a MongoDB filter string, a
hand-assembled JSON query document, JavaScript inside `$where` — lets an
attacker inject operators that change the query's meaning. The classic result
is authentication bypass (`{"$ne": null}` matching every user) or data
exfiltration. C# drivers ship typed query builders precisely so input stays a
value and can never become query syntax.

## Do this
1. Find the flagged query construction where user input is concatenated into
   the query.
2. Rebuild it with the driver's typed API (e.g.
   `Builders<User>.Filter.Eq(u => u.Name, userInput)`) so the input is always
   bound as a value, never parsed as syntax.
3. If raw query documents are unavoidable, validate the input against an
   allow-listed shape before it touches the query.
4. Test with an operator-injection payload and confirm it is treated as a
   literal value that matches nothing unintended.

## AVOID
- Do not sanitize by blacklisting `$`, quotes, or braces with
  `string.Replace` — bypasses are routine and the next driver version may add
  new operators. Use the typed builders so input can never become syntax.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
