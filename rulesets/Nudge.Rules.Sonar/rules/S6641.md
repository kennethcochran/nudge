# S6641 — Connection strings should not be vulnerable to injection attacks

## Why
The rule fires when untrusted input is concatenated or interpolated into a
connection string (e.g. `"Database=" + userDb`). A crafted value can break out
of the key/value grammar — a semicolon or quote in the input becomes a new
connection-string key, letting an attacker redirect the server, change the
database, or flip options like integrated security. Connection strings look
like plain text but are parsed as structured data, so building them with
string concatenation is injection by another name.

## Do this
1. Build the string with `DbConnectionStringBuilder` (or
   `SqlConnectionStringBuilder`) and assign each piece as a property
   (`builder["Database"] = value`) instead of concatenating text — the builder
   handles quoting and escaping of the grammar for you.
2. Validate the untrusted value against an allow-list (known database names,
   known servers) before it ever reaches the builder.
3. If the value can't be validated, don't put user input in the connection
   string at all — select from server-side configuration instead.

## AVOID
- Do not switch from `+` to `$"..."` interpolation and call it fixed —
  interpolation is the same concatenation with nicer syntax.
- Do not "sanitize" by stripping semicolons or quotes yourself; hand-rolled
  escaping of connection-string grammar is exactly what the builder exists
  to do, and yours will miss an edge case.
- Do not suppress with `#pragma warning disable` or `[SuppressMessage]`.
  Suppression of analyzer diagnostics is forbidden by the project's AGENTS.md.
